Git Repository Management for a Django Project

Introduction to Version Control in Web Engineering

In modern full-stack software development, a Version Control System (VCS) is fundamental. Web applications built using Django (a high-level Python web framework) consist of application logic, database models, static assets, configuration settings, and database schema migrations.

Git is a distributed version control system that tracks changes in files across three local states before synchronization with remote platforms like GitHub or GitLab:

  • Working Directory: The local sandbox on your filesystem where files are actively edited.
  • Staging Area (Index): A temporary preparation zone formatted as a manifest of files to be packaged into the next snapshot.
  • Git Repository (HEAD): The permanent database of cryptographically hashed (SHA-1) commit objects stored inside the hidden .git/ directory.
Working Directory git add Staging Area (Index) git commit Local Repository (HEAD) git push Remote (origin/main)

Django Project Anatomy & Version Control Boundaries

When you run django-admin startproject mysite and create an app with python manage.py startapp core, the file tree takes the following standard shape: 

mysite/
├── manage.py                # Command-line utility (MUST TRACK)
├── mysite/
│   ├── __init__.py          # Package marker (MUST TRACK)
│   ├── settings.py          # Project configuration (MUST TRACK - secrets abstracted)
│   ├── urls.py              # Root URL routing declarations (MUST TRACK)
│   ├── asgi.py & wsgi.py     # Server gateway interfaces (MUST TRACK)
├── core/
│   ├── models.py            # Database schema definitions (MUST TRACK)
│   ├── views.py             # HTTP request controllers (MUST TRACK)
│   ├── urls.py              # App-level routing (MUST TRACK)
│   └── migrations/          # Schema transition scripts (MUST TRACK)
│       ├── __init__.py
│       └── 0001_initial.py
├── .env                     # Local secrets and API keys (DO NOT TRACK!)
├── db.sqlite3               # Local test SQLite database (DO NOT TRACK!)
├── venv/                    # Virtual environment binaries (DO NOT TRACK!)
└── __pycache__/             # Compiled bytecode (DO NOT TRACK!)

Critical Django Files and Directories to Exclude from Version Control

Careless staging with git add . without an explicit .gitignore causes severe operational failures:

1. SQLite Database: db.sqlite3

SQLite is a file-based database. If committed:

  • Every single local test record, session token, or admin user created on your machine gets pushed to teammates.
  • Git treats SQLite as a binary file. Any concurrent database writes result in unresolvable binary merge conflicts and repository database corruption.
  • Production databases must always be external services (PostgreSQL, MySQL), provisioned via environment variables, not checked-in SQLite binaries.

2. Secrets & Environment Files: .env

The Django SECRET_KEY cryptographic salt, database credentials, AWS keys, and payment gateway tokens must never enter version control history. Committing a secret permanently persists it in the Git log tree, exposing it to anyone with repository read access even if deleted in a later commit.

3. Compiled Bytecode: __pycache__/ and *.pyc

Python compiles .py source code into bytecode files (.pyc) for runtime execution speed. These are machine-specific and Python version-specific. Committing bytecode causes phantom bugs where stale compiled files override new source edits.

4. Python Virtual Environments: venv/, .venv/, env/

Virtual environments contain thousands of compiled C-extensions, symlinks, and OS-specific executable binaries. Committing venv/ inflates the repository size by hundreds of megabytes and fails on teammates' machines running different OS kernels. Instead, dependencies must be documented in a text manifest: pip freeze > requirements.txt.

5. Media & Collected Static Files: media/ and staticfiles/

media/ holds user-uploaded content (profile avatars, documents) that belong in cloud object storage (e.g., AWS S3). staticfiles/ is generated during deployment by python manage.py collectstatic and represents a transient build artifact.

Authoring a Production-Grade Django .gitignore

A .gitignore file placed at the project root instructs Git which untracked files to intentionally ignore: 

# ==========================================
# Production-Grade .gitignore for Django

*.py[cod]
*$py.class
*.so

# 2. Virtual Environments

.venv/

Django Database Migrations in Version Control

A common point of confusion is whether to commit files inside migrations/ directories.

Rule: You MUST track Django migration files (e.g., 0001_initial.py, 0002_add_status_field.py).

Django migrations are Python source files that describe incremental, linear transformations of your database schema. Without them:

  • Teammates pulling your code cannot run python manage.py migrate to construct the tables required by your new models.
  • Continuous Integration (CI/CD) pipelines and production servers will fail to deploy.

The Split Migration Problem & Resolution

When Developer A creates migration 0002_add_bio.py on branch feature-user and Developer B creates migration 0002_add_avatar.py on branch feature-profile, merging their branches creates two migration nodes with the same predecessor.

Django detects this split dependency graph. The solution is running: 

python manage.py makemigrations --merge

This generates a clean merge migration file (e.g., 0003_merge_*.py) that unifies the branch heads.

Collaborative Branching Workflows (Git Flow)

In production teams, developers never push untested code directly to the primary branch. The standard lifecycle follows:

Branch Purpose Protection Rules
main / master Production-ready code matching live deployment. Protected. Requires approved pull requests and passing CI.
develop Integration branch where features accumulate prior to release. Internal testing & staging deployments.
feature/<name> Isolated branch created for a single feature or story. Branch off develop, deleted after merge.
hotfix/<name> Urgent patches applied directly to production. Merged into both main and develop.

Merge Conflicts Anatomy and Resolution

A merge conflict occurs when two branches modify the exact same line in a file in conflicting ways, or one branch deletes a file while another modifies it. Git pauses the merge and annotates the conflicting file with conflict markers: 

<<<<<<< HEAD (Current Branch: main)
urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/v1/auth/', include('authentication.urls')),
]
=======
urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/v1/polls/', include('polls.urls')),
]
>>>>>>> feature/polls (Incoming Branch)

Three-Step Resolution:

  1. Inspect & Decide: Open the file and determine what the integrated logic should look like (in this case, both URL routes are needed).
  2. Remove Markers: Manually delete the <<<<<<<, =======, and >>>>>>> lines and preserve the desired code: 
    urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/v1/auth/', include('authentication.urls')),
    path('api/v1/polls/', include('polls.urls')),
]
  3. Stage & Commit: Run git add mysite/urls.py followed by git commit -m "chore: resolve URL routing merge conflict".

Essential Git Commands Reference

Command Operational Description
git init Initializes a new empty Git repository inside the current directory (creates .git/).
git status Displays the working directory state: untracked, modified, or staged files.
git add <file> / git add . Stages changes from the working tree into the Staging Index for the next commit snapshot.
git commit -m "message" Records staged snapshots permanently into the repository history with an explanatory message.
git branch Lists local branches; asterisk (*) marks the currently active branch.
git checkout -b <branch> Creates a new branch and immediately switches the HEAD pointer to it.
git merge <branch> Combines changes from the target branch into the currently checked-out branch.
git log --oneline --graph Displays the commit timeline as a visual ASCII graph with abbreviated SHA hashes.
git rm --cached <file> Untracks a file from Git while preserving the physical file in your local workspace.
