Git Repository Management for a Django Project

Follow this step-by-step procedure to create a robust Git-managed Django project. You can practice these exact commands inside the Simulation tab.

Scaffold the Django Project

Begin by creating an isolated directory, activating a virtual environment, and scaffolding a clean Django project named mysite:

$ mkdir django-lab && cd django-lab
$ python -m venv venv
$ source venv/bin/activate    # On Windows: venv\Scripts\activate
$ pip install django
$ django-admin startproject mysite .
$ python manage.py migrate     # Generates local db.sqlite3

Initialize Git Repository

Initialize the Git tracking database inside the project root:

$ git init
Initialized empty Git repository in /home/student/django-lab/.git/

Verify that the default branch is set to main:

$ git branch -M main

Author the .gitignore File BEFORE Staging

Crucial Rule: Never run git add . until your .gitignore is in place. Once an untracked file is staged or committed, adding it to .gitignore later does not remove it from Git tracking!

Create .gitignore in the project root directory with the following contents:

# Virtual Environments
venv/
.venv/
env/

# Python Bytecode & Cache
__pycache__/
*.py[cod]

# Local Database (Never track SQLite binary!)
db.sqlite3
*.sqlite3

# Environment Secrets
.env
local_settings.py

# Media & Collected Static Files
media/
staticfiles/

Verify Status and Create Initial Baseline Commit

Inspect the working tree. Notice that db.sqlite3 and venv/ are completely ignored:

$ git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	manage.py
	mysite/

nothing added to commit but untracked files present

Stage the verified source files and craft an atomic initial commit:

$ git add .
$ git commit -m "chore: initialize django project with standard gitignore"
[main (root-commit) 4a7bc12] chore: initialize django project with standard gitignore
 6 files changed, 142 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 manage.py
 create mode 100644 mysite/__init__.py
 create mode 100644 mysite/asgi.py
 create mode 100644 mysite/settings.py
 create mode 100644 mysite/urls.py
 create mode 100644 mysite/wsgi.py

Create an Isolated Feature Branch

In team development, new features are built on dedicated branches rather than committing directly to main:

$ git checkout -b feature/polls-app
Switched to a new branch 'feature/polls-app'

Develop an App and Commit Model Migrations

Generate a new Django app named polls and define your models in polls/models.py:

$ python manage.py startapp polls

Register 'polls' in mysite/settings.py under INSTALLED_APPS, then generate schema migrations:

$ python manage.py makemigrations polls
Migrations for 'polls':
  polls/migrations/0001_initial.py
    - Create model Question
    - Create model Choice

Stage both the application code AND the migration file, then commit:

$ git add polls/ mysite/settings.py
$ git commit -m "feat(polls): add question and choice models with initial schema migration"

Merge Feature Branch into Main

Switch back to main and merge the completed feature branch:

$ git checkout main
Switched to branch 'main'

$ git merge feature/polls-app
Updating 4a7bc12..c89ef34
Fast-forward
 mysite/settings.py               |  1 +
 polls/models.py                  | 18 ++++++++++++++++++
 polls/migrations/0001_initial.py | 32 ++++++++++++++++++++++++++++++++
 3 files changed, 51 insertions(+)

Simulate and Resolve a Merge Conflict

Suppose another branch modified mysite/urls.py simultaneously. When merging, Git signals a conflict:

$ git merge feature/api-routes
Auto-merging mysite/urls.py
CONFLICT (content): Merge conflict in mysite/urls.py
Automatic merge failed; fix conflicts and then commit the result.

Open mysite/urls.py. Look for the conflict markers:

<<<<<<< HEAD
path('polls/', include('polls.urls')),
=======
path('api/v1/', include('api.urls')),
>>>>>>> feature/api-routes

Resolve the conflict by keeping both routes and removing the divider markers:

path('polls/', include('polls.urls')),
path('api/v1/', include('api.urls')),

Mark the conflict as resolved by staging and committing:

$ git add mysite/urls.py
$ git commit -m "chore: resolve URL routing conflict between polls and api"

Create an Annotated Release Tag

Tag the production-ready state with a semantic version number:

$ git tag -a v1.0.0 -m "Release version 1.0.0 with Polls application"
$ git tag
v1.0.0
